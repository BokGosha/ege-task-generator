# Тестирование системы

## Цели тестирования

Тестирование подсистемы автоматической генерации заданий ЕГЭ преследует
четыре цели:

1. **Корректность математического ядра.** Параметры заданий 7 и 11
   генерируются вероятностно, поэтому ответ должен независимо вычисляться
   двумя путями (генератором и калькулятором эталонного ответа), а не
   вытаскиваться из одного источника правды.
2. **Устойчивость к сбоям LLM.** Внешние модели (YandexGPT, GigaChat) —
   ненадёжный компонент: таймауты, ошибки сети, некорректный JSON. Эти
   сценарии нельзя пускать в production без явного покрытия.
3. **Соответствие HTTP-контракту.** Схемы запросов и ответов фиксированы
   спецификацией; любое расхождение между Pydantic-моделями и реальными
   ответами эндпоинтов ломает клиентов.
4. **Поведение под нагрузкой.** Целевой профиль 10–50 одновременных
   пользователей должен выдерживаться без 5xx и без лавинообразного
   роста latency.

## Стратегия и пирамида тестов

В проекте применена классическая пирамида тестирования с четырьмя
уровнями. Каждый уровень имеет собственный каталог в `tests/`, собственные
зависимости и собственный объём ответственности.

| Уровень        | Каталог              | Объект            | Зависимости               |
|----------------|----------------------|-------------------|---------------------------|
| Юнит-тесты     | `tests/unit/`        | Функция / класс   | Моки, без БД              |
| Контрактные    | `tests/contract/`    | Pydantic-схемы    | Без БД и HTTP             |
| Интеграционные | `tests/integration/` | Полный конвейер   | PostgreSQL + ASGI-клиент  |
| Нагрузочные    | `tests/load/`        | Запущенный сервис | Docker Compose + Locust   |

Распределение по уровням намеренно асимметрично: больше всего проверок
сосредоточено на быстрых юнит-тестах, а медленные интеграционные тесты
покрывают только сценарии, которые невозможно воспроизвести в изоляции
(работа с БД, HTTP-конвейер, обработка ошибок через middleware).

## Юнит-тесты

Юнит-тесты выполняются без поднятия БД и внешних сервисов. LLM-провайдеры
заменяются на детерминированный `MockLlmAdapter`, БД-сессия — на
`MagicMock` с асинхронными методами.

| Файл | Что проверяет |
|---|---|
| `test_answer_calculator.py` | Детерминированность `calculate_answer`: одни и те же входные параметры дают одинаковый ответ при многократных вызовах. Параметризован по подтипам заданий 7 и 11. |
| `test_generators_task7.py` | Генератор задания 7: покрытие всех подтипов, согласованность с собственным валидатором (20 прогонов на подтип), кросс-проверка с `calculate_answer`, граничные условия `is_valid_params_7` (отрицательный ответ, переполнение `BIGINT`, NaN/Inf, неизвестный подтип). |
| `test_generators_task11.py` | Аналогичный набор проверок для задания 11. |
| `test_llm_adapter.py` | Фабрика `get_llm_adapter`, поведение `MockLlmAdapter`, защитный слой `_call_llm_with_guards`: таймаут не ретраится, транспортные ошибки ретраятся ровно `LLM_RETRY_ATTEMPTS` раз, семафор ограничивает параллельные вызовы. |
| `test_param_generator_service.py` | Сервис генерации параметров: happy path, retry-цикл при отклонении валидатором, исчерпание попыток (`ParamRetryExhaustedError`), запись `ParamGenerationAudit` для каждой неудачной попытки, кросс-проверка ответа с `calculate_answer`. |
| `test_task_orchestrator_pipeline.py` | Оркестратор конвейера: установка `failure_stage` в `generation` или `validation` в зависимости от того, на каком шаге упал LLM; передача `feedback_text()` валидатора в `previous_feedback` следующей итерации генератора; ровно `MAX_LLM_ITERATIONS` итераций при сценарии «всё отклонено». |
| `test_wording_generator_prompt.py` | Сборка промпта для LLM: включение типа, подтипа, эталонного ответа, параметров (без служебных ключей), few-shot примеров и секции обратной связи при наличии `previous_feedback`. |
| `test_wording_numeric_check.py` | Детерминированная численная проверка формулировки: `find_missing_params` находит отсутствующие в тексте числовые параметры, `format_feedback` формирует подсказку для генератора. |
| `test_wording_validator.py` | `ValidationResult.is_accepted` (True только при всех 5 критериях True), `failed_criteria()`, `feedback_text()`, парсинг частичных JSON-ответов LLM, оборачивание произвольных исключений в `LlmValidationError` с пробросом `task_id`. |

Отдельный класс `TestStressBigIntBounds` в обоих тестах генераторов
прогоняет по 50 случайных параметризаций на подтип и проверяет, что
ответ укладывается в `BIGINT`. Это страховка от регрессии после расширения
типа `reference_answer` в БД.

## Контрактные тесты

Контрактные тесты выполняются без HTTP-клиента и без БД: они работают
с Pydantic-моделями напрямую. Цель — гарантировать, что схемы ответов
не «расползаются» при рефакторинге.

`tests/contract/test_openapi_compliance.py` проверяет:

- набор полей в `GenerateTaskSuccessResponse` совпадает с зафиксированным
  списком из 11 ключей;
- `QualityProfileResponse` содержит ровно 5 критериев + `verdict` +
  `diagnostic_message`;
- `CriterionResult` сериализуется через alias `pass`/`pass_`;
- допустимы nullable-поля при `status="error"` (отсутствие
  `final_wording`, `quality_profile`);
- структура `TaskListResponse`, `HistoryResponse`, `TaskListItem`,
  `HistoryItem`.

## Интеграционные тесты

Интеграционные тесты используют реальную PostgreSQL (URL берётся из
`settings.database_url`) и ASGI-транспорт `httpx.AsyncClient`. Перед
каждым тестом сбрасывается счётчик `slowapi.limiter`, после теста —
`session.rollback()`. Для всех тестов LLM принудительно заменён на
`mock`-провайдер.

| Файл | Объект тестирования                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
|---|-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `test_generate_api.py` | Happy path `POST /api/v1/tasks/generate` для задач 7 и 11: структура ответа, сортировка итераций по `attempt_no` ASC, наличие `quality_profile` со всеми критериями. Ошибки: 400 на неизвестный `task_type`/`subtype`, 422 на нарушение схемы, 415/422 на неверный `Content-Type`. Эндпоинт `/statistics`: структура, фильтры по датам, 400 на инвертированный диапазон, сумма долей статусов = 1. Приёмочный тест производительности: полный цикл должен укладываться в 90 секунд при mock-LLM. |
| `test_tasks_crud.py` | `GET /api/v1/tasks/{id}` (200, 404, error body), `GET /api/v1/tasks` (фильтры по датам, поля краткой карточки).                                                                                                                                                                                                                                                                                                                                                                                       |
| `test_history.py` | `GET /api/v1/tasks/history`: пагинация, фильтры по `task_type` и `status`, поля элементов истории.                                                                                                                                                                                                                                                                                                                                                                                                    |
| `test_export.py` | `GET /api/v1/export/tasks/{id}` для форматов JSON, TXT, PDF: корректный `Content-Type`, валидный заголовок PDF (`%PDF`), 404 на несуществующее задание.                                                                                                                                                                                                                                                                                                                                               |
| `test_persistence.py` | Согласованность БД-слоя: при `accepted` в БД лежат `Task`, `TaskIteration` (последняя со статусом `accepted`), `TaskQuality` с `verdict='accepted'` и хотя бы два `LlmCall` (`wording_generation` + `semantic_validation`); при `rejected` — три итерации со статусом `rejected` и непустой список `RejectionReason`; терминальные статусы неизменны при повторном чтении.                                                                                                                            |
| `test_param_audit.py` | При retry генерации параметров в `ParamGenerationAudit` создаётся запись с `attempt_number=1` и зафиксированной причиной отклонения; при успехе с первой попытки записей нет.                                                                                                                                                                                                                                                                                                                         |
| `test_rejection_loop.py` | При всех отклонённых валидатором итерациях задание получает `status="rejected"` и ровно 3 итерации; при принятии на 2-й итерации — 2 итерации и `status="accepted"`; `previous_feedback` корректно прокидывается из валидатора в генератор.                                                                                                                                                                                                                                                           |
| `test_llm_error_handling.py` | `LlmTimeoutError` на стадии генерации и валидации возвращает HTTP 504 с кодом `LLM_TIMEOUT`; `task_id` присутствует в `error.details`; `LlmGenerationError`/`LlmValidationError` возвращают 500 с соответствующими кодами.                                                                                                                                                                                                                                                                            |
| `test_rate_limit.py` | При искусственно заниженном лимите (2/min) запросы сверх лимита получают HTTP 429 с кодом `RATE_LIMIT_EXCEEDED` и заголовком `Retry-After`. Использует подмену `_route_limits` через фикстуру.                                                                                                                                                                                                                                                                                                        |
| `test_middleware_request_id.py` | Middleware `X-Request-ID`: переданный заголовок эхом возвращается в ответе; при отсутствии — генерируется валидный UUID.                                                                                                                                                                                                                                                                                                                                                                              |
| `test_generate_stats.py` | Изоляция параллельных запросов: четыре `asyncio.gather`-вызова `POST /generate` дают четыре независимых `task_id`, итерации каждого задания принадлежат только ему.                                                                                                                                                                                                                                                                                                                                   |

Тестовая инфраструктура (`tests/integration/conftest.py`) предоставляет
три фикстуры: `test_engine` (создаёт схему БД через
`Base.metadata.create_all`), `db_session` (откатывается после теста),
`client` (ASGI `httpx.AsyncClient` с переопределённой зависимостью
`get_db`).

## Нагрузочное тестирование

Нагрузочные тесты вынесены в `tests/load/` и используют **Locust**.
Сценарий `locustfile.py` моделирует виртуального пользователя,
вызывающего `POST /api/v1/tasks/generate` со случайным выбором между
заданиями 7 и 11; интервал между запросами `between(3, 7)` секунд
имитирует естественное поведение клиента и не упирается мгновенно в
`RATE_LIMIT_PER_MINUTE`.

Профили запуска:

- **Smoke** — 5 пользователей, 2 минуты: проверка работоспособности.
- **Целевой** — 50 пользователей, плавная рампа, 5 минут.

Прогон автоматически фейлится (`exit code 1`), если:
- доля провалов превышает 1 %;
- p95 latency превышает 180 секунд.

Коды ответов 200 и 429 считаются успешными (429 — ожидаемая реакция
rate limiter на превышение клиентского лимита, не сбой системы);
сбоем считаются 502/503/504 и любые другие неожиданные коды.

Сценарий читает заголовок `X-Request-ID` из ответа и пишет его в текст
ошибки, что позволяет коррелировать падения нагрузочного теста с
логами в Grafana/Loki.

## Инструменты и окружение

| Назначение                  | Инструмент |
|-----------------------------|---|
| Тестовый раннер             | pytest, pytest-asyncio |
| HTTP-клиент в тестах        | httpx + ASGITransport |
| БД для интеграционных тестов | PostgreSQL 15 (через `DATABASE_URL`) |
| Моки и патчинг              | unittest.mock (MagicMock, AsyncMock, patch) |
| Нагрузочное тестирование    | Locust ≥ 2.20 |
| Линтер / форматтер          | ruff |

LLM-провайдеры в тестах принудительно заменены на `MockLlmAdapter`,
который возвращает детерминированные строки с префиксом `[MOCK]` и
фиксированный `last_token_usage`. Это исключает зависимость тестов от
сетевой доступности YandexGPT/GigaChat и от их квот, а также делает
интеграционные тесты воспроизводимыми.

## Запуск

```bash
# Все тесты
pytest

# Только юнит
pytest tests/unit/

# Только интеграционные (требует поднятой PostgreSQL)
pytest tests/integration/

# Контрактные
pytest tests/contract/

# Нагрузочные (требует docker compose up)
locust -f tests/load/locustfile.py --host http://localhost:8000 --headless --users 50 --spawn-rate 1 --run-time 5m
```

## Резюме

Подсистема тестирования закрывает все четыре стратегические цели:

- **корректность ядра** — обеспечивается параметризованными юнит-тестами
  генераторов с двойной проверкой ответа и стресс-прогонами на границах
  типов;
- **устойчивость к сбоям LLM** — покрыта на двух уровнях: изолированно
  через `_call_llm_with_guards` и сквозно через подмену методов
  `WordingGenerator.generate` / `WordingValidator.validate` в
  интеграционных тестах;
- **соответствие контракту** — фиксируется контрактными тестами на
  Pydantic-схемах, что не позволяет молча изменить структуру ответа;
- **поведение под нагрузкой** — измеряется Locust-сценарием с
  автоматической проверкой порогов p95 latency и доли ошибок.
